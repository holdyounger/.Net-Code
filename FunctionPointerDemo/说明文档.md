# FunctionPointerDemo 说明文档

> **一句话**：验证 `RuntimeMethodHandle.GetFunctionPointer()` 到底返回了什么，以及如何从 precode(stub) 解析出真实的 JIT native code。

---

## 1. 项目动机

在 .NET RASP（运行时应用自保护）和 Hook 框架中，一个核心需求是：**拿到一个方法的真实机器码入口地址**。

`RuntimeMethodHandle.GetFunctionPointer()` 是最常用的 API，但它返回的地址**不一定是真实 JIT 代码**——在很多场景下返回的是 **precode（前置桩/stub）**，真实代码需要进一步解码才能拿到。

这个 Demo 项目就是为了**清楚地展示这一层间接性**，并实现跨运行时的 precode 解析。

---

## 2. 核心概念

### 2.1 GetFunctionPointer 返回什么？

`GetFunctionPointer()` 内部调用 `MethodDesc::GetMultiCallableAddrOfCode`（`src/coreclr/vm/runtimehandles.cpp:1306`）。它的返回值取决于方法当前的状态：

| 方法状态 | 返回值 | 说明 |
|---------|--------|------|
| 已 JIT，无 precode | 真实 native code | `entry == realCode` |
| 已 JIT，有 precode | precode stub 地址 | 需要解码才能拿到 realCode |
| 未 JIT | precode stub 地址 | 调用时触发 JIT |

### 2.2 Precode 是什么？

Precode 是 CLR 在方法和真实代码之间插入的一层**跳板**。它是一小段机器码 + 数据页，作用是：

- **延迟 JIT**：方法首次调用时，precode 指向 Prestub，Prestub 触发 JIT 编译后回填 Target
- **NGEN/R2R 绑定**：预编译代码通过 precode 做间接跳转，支持运行时绑定

### 2.3 两种 Precode 类型

**FixupPrecode**（NGEN/R2R 常见，.NET 9 中普通方法也常见）：

```
; x64 机器码模板 (thunktemplates.asm:19)
jmp  qword ptr [rip+disp32]       ; FF 25 xx xx xx xx  → data.Target
mov  r10, qword ptr [rip+disp32]  ; 4C 8B 15 xx xx xx xx → data.MethodDesc
jmp  qword ptr [rip+disp32]       ; FF 25 xx xx xx xx  → data.PrecodeFixupThunk
```

数据页布局：`{ Target(+0); MethodDesc(+8); PrecodeFixupThunk(+16) }`

**StubPrecode**（普通 JIT 方法）：

```
; x64 机器码模板 (thunktemplates.asm:14)
mov  r10, qword ptr [rip+disp32]  ; 4C 8B 15 xx xx xx xx → data.SecretParam (MethodDesc)
jmp  qword ptr [rip+disp32]       ; FF 25 xx xx xx xx  → data.Target
```

数据页布局：`{ SecretParam(+0); Target(+8); Type(+16) }`

## 6. 输出解读

每类方法输出格式：

```
========== 普通实例方法 Add (JIT后) ==========
  entry         = 0x7FFEEBF78AF8    ← GetFunctionPointer() 的原始返回值
  isPrecode     = True              ← 是否为 precode
  precodeType   = FixupPrecode      ← precode 类型
  methodDesc    = 0x7FFEDBDE43E8    ← MethodDesc 地址（来自 MethodHandle.Value）
  realCode      = 0x7FFEEBC9C010    ← 跟随 precode 后的真实 native code
  entry==realCode= False            ← entry ≠ realCode，说明中间有 precode
  entry bytes:  FF 25 1A 3F 00 00 4C 8B 15 21 3F 00 00 FF 25 24
  data page:    00 C0 F1 EB FE 7F 00 00 E8 43 DE DB FE 7F 00 00
  real bytes:   55 57 48 83 EC 28 48 8B EC 48 89 4D 40 48 89 55
```

### 关键判断

- **`entry == realCode`** → `GetFunctionPointer` 直接返回了真实代码（无 precode）
- **`entry != realCode`** → entry 是 precode stub，需要解码
- **`real bytes` 以 `55`（push rbp）开头** → 典型的 JIT 函数 prologue，确认是真实代码
- **`methodDesc` 全部有值** → 通过 `MethodHandle.Value` 获取，不依赖 precode 解码

## 7. 解析原理

### 7.1 CoreCLR 分支 (net9.0, x64)

`ResolveCoreCLRNativeCode` → `ResolveOneStepCoreCLR`：

1. **特征码匹配**：读 entry 前几个字节，判断 precode 类型
   - `4C 8B 15 ... FF 25 ...` → StubPrecode
   - `FF 25 ... 4C 8B 15 ...` → FixupPrecode
2. **从指令解码数据页地址**（rip-relative）：
   - `jmp [rip+disp32]` → `data = entry + 6 + disp32`
   - `mov r10,[rip+disp32]` → `data = entry + 7 + disp32`
   - **不依赖硬编码页偏移**，任何页大小都正确
3. **读数据页**获取 Target（真实代码）和 MethodDesc
4. **多跳跟随**：若 Target 仍指向另一个 precode，继续跟随（最多 8 跳）

### 7.2 .NET Framework 分支 (net48, x86/x64)

`ResolveFrameworkNativeCode` → `ResolveOneStepFramework`：

**x64**：与 CoreCLR 同源（同一套 `thunktemplates.asm`），直接复用 `ResolveOneStepCoreCLR`，另识别 `E9/E8` 纯跳板。

**x86**：特征码不同：

| Precode 类型 | x86 机器码 | 特征 |
|-------------|-----------|------|
| StubPrecode | `A1 <SecretParam槽> FF 25 <Target槽>` | `A1` = mov eax, [abs32] |
| FixupPrecode | `FF 25 <Target槽> A1 <MD槽> FF 25 <Thunk槽>` | 先 jmp 再 mov |

x86 的指令编码是**绝对地址**（非 rip-relative），直接读槽地址里的指针即可。

### 7.3 MethodDesc 获取

**统一使用 `mi.MethodHandle.Value`**，不依赖 precode 解码：

- `RuntimeMethodHandle.Value` 直接返回该方法的 **MethodDesc 指针**（CLR 内部句柄）
- net48 和 net9.0 语义一致
- **任何 entry 形态都能拿到**——包括 E9 跳板（跳板里不内嵌 MD，纯特征码解码拿不到）

在 `Show` 方法中，`MethodHandle.Value` 的值会**覆盖**解码结果：

```csharp
IntPtr mdHandle = mi.MethodHandle.Value;
if (mdHandle != IntPtr.Zero)
    result.MethodDesc = mdHandle;  // 覆盖解码结果
```

## 8. RealCode 查询依据（源码级追溯）

RealCode 的获取不是凭空猜测，而是严格遵循 CoreCLR 源码中的调用链。以下是从 `GetFunctionPointer()` 到最终拿到真实 native code 的**完整解码路径**，每一步都标注源码位置。

### 8.1 入口：GetFunctionPointer → GetMultiCallableAddrOfCode

托管代码调用 `mi.MethodHandle.GetFunctionPointer()` 时，CLR 内部走的是：

```
RuntimeMethodHandle.GetFunctionPointer()  （托管 API）
  → RuntimeMethodHandle_GetFunctionPointer  （QCall 入口）
    → MethodDesc::GetMultiCallableAddrOfCode(accessFlags)
```

**源码位置**（`runtimehandles.cpp`）：

```cpp
// runtimehandles.cpp:1321
extern "C" void * QCALLTYPE RuntimeMethodHandle_GetFunctionPointer(MethodDesc * pMethod)
{
    // ...
    funcPtr = (void*)pMethod->GetMultiCallableAddrOfCode(CORINFO_ACCESS_UNMANAGED_CALLER_MAYBE);
    // ...
}
```

### 8.2 决策：TryGetMultiCallableAddrOfCode — 返回 precode 还是真实代码？

`GetMultiCallableAddrOfCode` 调用 `TryGetMultiCallableAddrOfCode`，后者是**核心决策点**：

**源码位置**（`method.cpp:2245`）：

```cpp
// method.cpp:2245
PCODE MethodDesc::TryGetMultiCallableAddrOfCode(CORINFO_ACCESS_FLAGS accessFlags)
{
    // ...（省略泛型/FCall/EnC 等特殊路径）

    // ① 如果方法已指向稳定的 native code，直接返回 native code
    if (IsPointingToStableNativeCode())
        return GetNativeCode();          // ← entry == realCode 的情况

    // ② 如果已有稳定入口（precode 已创建）
    if (HasStableEntryPoint())
        return GetStableEntryPoint();    // ← 返回 precode stub 地址

    // ③ 否则创建 precode
    GetOrCreatePrecode();
    return GetStableEntryPoint();        // ← 返回新创建的 precode
}
```

**关键结论**：`GetFunctionPointer()` 的返回值（entry）有三种可能：

| 决策分支 | 返回值 | entry == realCode? |
|---------|--------|-------------------|
| `IsPointingToStableNativeCode` → `GetNativeCode()` | 真实 JIT 代码 | ✅ 是 |
| `HasStableEntryPoint` → `GetStableEntryPoint()` | precode stub | ❌ 否 |
| `GetOrCreatePrecode` → 新建 precode | precode stub | ❌ 否 |

### 8.3 GetNativeCode — 什么时候返回 NULL？

`GetNativeCode()` 在有 precode 时返回 NULL，这就是为什么 `TryGetMultiCallableAddrOfCode` 会走分支 ② 返回 precode 而非 native code：

**源码位置**（`method.cpp:1104`）：

```cpp
// method.cpp:1104
PCODE MethodDesc::GetNativeCode()
{
    LIMITED_METHOD_DAC_CONTRACT;

    if (HasNativeCodeSlot())
    {
        return MaybeGetNativeCode();
    }
    // ...
}
```

> 当方法有 precode 但尚未 JIT 或 JIT 后通过 precode 间接指向时，`GetNativeCode` 返回的地址与 precode 的 Target 槽位一致；但首次调用前 Target 指向 Prestub，此时 entry ≠ realCode。

### 8.4 Precode 数据页布局（CoreCLR 源码）

RealCode 的解码完全依赖 precode 数据页的结构。以下是 CoreCLR 源码中的定义：

**StubPrecodeData**（`precode.h:24-30`）：

```cpp
// precode.h:24
struct StubPrecodeData
{
    TADDR SecretParam;   // +0  → MethodDesc 指针（Stub 类型）
    PCODE Target;        // +8  → 真实代码地址 或 Prestub
    TADDR Type;          // +16 → precode 类型标识
};
```

**FixupPrecodeData**（`precode.h:376-381`）：

```cpp
// precode.h:376
struct FixupPrecodeData
{
    PCODE Target;              // +0  → 真实代码地址
    class MethodDesc *MethodDesc; // +8  → MethodDesc 指针
    PCODE PrecodeFixupThunk;   // +16 → 修复跳转 thunk
};
```

### 8.5 Precode 机器码模板（thunktemplates.asm）

x64 汇编模板定义在 `thunktemplates.asm`，这是**特征码匹配的权威依据**：

```asm
; thunktemplates.asm (amd64)

LEAF_ENTRY StubPrecodeCode, _TEXT
        mov    r10, QWORD PTR [DATA_SLOT(StubPrecode, SecretParam)]
        jmp    QWORD PTR [DATA_SLOT(StubPrecode, Target)]
LEAF_END_MARKED StubPrecodeCode, _TEXT

LEAF_ENTRY FixupPrecodeCode, _TEXT
        jmp QWORD PTR [DATA_SLOT(FixupPrecode, Target)]
        mov    r10, QWORD PTR [DATA_SLOT(FixupPrecode, MethodDesc)]
        jmp QWORD PTR [DATA_SLOT(FixupPrecode, PrecodeFixupThunk)]
LEAF_END_MARKED FixupPrecodeCode, _TEXT
```

汇编到机器码后：

| Precode 类型 | 第一条指令 | 机器码 | 数据页偏移计算 |
|-------------|-----------|--------|---------------|
| StubPrecode | `mov r10, [rip+disp32]` | `4C 8B 15 xx xx xx xx` | `data = entry + 7 + disp32` |
| StubPrecode | `jmp [rip+disp32]` | `FF 25 xx xx xx xx` | `data = entry + 6 + disp32` |
| FixupPrecode | `jmp [rip+disp32]` | `FF 25 xx xx xx xx` | `data = entry + 6 + disp32` |
| FixupPrecode | `mov r10, [rip+disp32]` | `4C 8B 15 xx xx xx xx` | `data = entry + 7 + disp32` |

> `DATA_SLOT` 宏展开后，数据页位于代码页之后的 `STUB_PAGE_SIZE`（x64 = 16384 字节）偏移处。但本 Demo **不从硬编码页偏移算数据页地址**，而是直接从指令编码的 `rip+disp32` 解码——这样无论页大小如何都正确。

### 8.6 CLR 如何从 entry 反查 Precode — GetPrecodeFromEntryPoint

CLR 自身也有从 entry 地址反查 precode 的需求（如调试器、GC）。`Precode::GetPrecodeFromEntryPoint` 是 CLR 的官方实现：

**源码位置**（`precode.h:760`）：

```cpp
// precode.h:760
static PTR_Precode GetPrecodeFromEntryPoint(PCODE addr, BOOL fSpeculative = FALSE)
{
    // 尝试 StubPrecode
    if (!StubPrecode::IsStubPrecodeByASM(addr))
    {
        // 尝试 FixupPrecode
        if (!FixupPrecode::IsFixupPrecodeByASM(addr))
        {
            // 不是 precode
            return NULL;
        }
        return AsFixupPrecode(addr);
    }
    return AsStubPrecode(addr);
}
```

本 Demo 的 `ResolveOneStepCoreCLR` 做的是**同样的事情**：用特征码判断 precode 类型 → 解码数据页 → 取出 Target。

### 8.7 CLR 取 RealCode 的官方方法 — GetTarget / GetNativeCode

CLR 自身取真实代码地址的函数：

**Precode::GetTarget**（`precode.cpp:702`）：

```cpp
// precode.cpp:702
PCODE Precode::GetTarget()
{
    PrecodeType precodeType = GetType();
    switch (precodeType)
    {
    case PRECODE_STUB:
        target = AsStubPrecode()->GetTarget();    // → GetData()->Target
        break;
    case PRECODE_FIXUP:
        target = AsFixupPrecode()->GetTarget();   // → GetData()->Target
        break;
    // ...
    }
    return target;
}
```

**StubPrecode::GetTarget**（`precode.h:162`）：

```cpp
// precode.h:162
PCODE GetTarget()
{
    LIMITED_METHOD_DAC_CONTRACT;
    return GetData()->Target;    // 直接读数据页 +8 偏移
}
```

**FixupPrecode::GetTarget**（`precode.h:436`）：

```cpp
// precode.h:436
PCODE GetTarget()
{
    LIMITED_METHOD_DAC_CONTRACT;
    return GetData()->Target;    // 直接读数据页 +0 偏移
}
```

本 Demo 的解码逻辑与 CLR 完全一致：

| Precode 类型 | CLR 函数 | Demo 对应代码 | 数据页 Target 偏移 |
|-------------|----------|-------------|-------------------|
| StubPrecode | `GetData()->Target` (+8) | `ReadPtr(data + 8)` | +8 |
| FixupPrecode | `GetData()->Target` (+0) | `ReadPtr(data + 0)` | +0 |

### 8.8 完整解码链路图

```
托管层:  MethodInfo.MethodHandle.GetFunctionPointer()
              │
              ▼
QCall:   RuntimeMethodHandle_GetFunctionPointer(pMethod)    [runtimehandles.cpp:1321]
              │
              ▼
CLR:     MethodDesc::GetMultiCallableAddrOfCode()          [method.cpp:2192]
              │
              ▼
CLR:     MethodDesc::TryGetMultiCallableAddrOfCode()       [method.cpp:2245]
              │
              ├── IsPointingToStableNativeCode? ──→ GetNativeCode()  → entry == realCode ✅
              │
              └── HasStableEntryPoint? ──→ GetStableEntryPoint() → entry = precode stub
                                              │
                                              ▼
Demo 解码:  ResolveOneStepCoreCLR(entry)
              │
              ├── 特征码 FF 25 ... 4C 8B 15 ... → FixupPrecode
              │       data = entry + 6 + disp32
              │       realCode = ReadPtr(data + 0)  ← 与 FixupPrecode::GetTarget() 一致
              │
              ├── 特征码 4C 8B 15 ... FF 25 ... → StubPrecode
              │       data = entry + 7 + disp32
              │       realCode = ReadPtr(data + 8)  ← 与 StubPrecode::GetTarget() 一致
              │
              └── 其它 → entry 就是 realCode（非 precode）
```

### 8.9 .NET Framework 的对应关系

.NET Framework（net48）的 precode 机制与 CoreCLR **同源**：

- x64：机器码模板完全一致（同一套 `thunktemplates.asm`），数据页布局相同
- x86：指令编码不同（用绝对地址 `A1 <槽>` / `FF 25 <槽>` 而非 rip-relative），但数据页语义相同

.NET Framework 的源码在 `referencesource` 仓库中可见（`src/vm/precode.h` / `src/vm/i386/thunktemplates.asm`），结构与 CoreCLR 对应：

| CoreCLR | .NET Framework | 差异 |
|---------|---------------|------|
| `StubPrecodeData { SecretParam; Target; Type }` | 相同 | 无 |
| `FixupPrecodeData { Target; MethodDesc; PrecodeFixupThunk }` | 相同 | 无 |
| x64: `4C 8B 15 <disp32>` (rip-relative) | 相同 | 无 |
| x86: N/A | `A1 <abs32> FF 25 <abs32>` | x86 用绝对地址 |

## 9. 安全设计

### 9.1 内存可读性检查

所有原生内存读取都经过 `IsReadable()` 保护：

```csharp
static bool IsReadable(long addr)
{
    VirtualQuery((IntPtr)addr, out var mbi, ...);
    // 检查：MEM_COMMIT + 非 PAGE_NOACCESS + 非 PAGE_GUARD
}
```

避免读到不可访问地址时 `AccessViolation` 直接崩进程。

### 9.2 读取辅助

| 函数 | 实现 | 说明 |
|------|------|------|
| `ReadByte` | `Marshal.ReadByte` | 单字节读取 |
| `ReadPtr` | `Marshal.ReadIntPtr` | 指针读取（8字节 x64 / 4字节 x86） |
| `ReadInt32` | `Marshal.ReadInt32` | 4字节有符号整数 |
| `ReadDisp32` | = `ReadInt32` | 解码 rip 相对偏移（有符号 32 位） |

### 9.3 防死循环

precode 跟随最多 8 跳，且每跳检查 `step.RealCode != cur` 防止无进展死循环。

| **x86 支持** | ✅ | ✅ |

FunctionPointerDemo 是 HookInfo.cs 中 precode 解析逻辑的**独立验证版**，用更清晰的代码结构展示同一套技术原理。

## 13. 常见问题

### Q: 为什么 entry 有时等于 realCode？

方法已被 JIT 且 CLR 决定不使用 precode（如 `PrepareMethod` 后的 net48 x64 场景），`GetFunctionPointer` 直接返回真实代码。

### Q: P/Invoke 的 realCode 是真正的 Win32 函数吗？

**不是**。P/Invoke 返回的是 NDirect IL stub（StubPrecode），`realCode` 是这个 stub 的代码，不是 `kernel32.dll` 里的真实函数。要拿真正的 Win32 函数地址，需要解码 NDirect stub 的后续结构。

### Q: 为什么 x86 要在 Windows 侧运行？

WSL2 interop 会把 32 位 exe 强制拉成 64 位宿主进程，`Environment.Is64BitProcess` 变成 True，走 x64 分支而不是 x86 分支。`run-net48-x86.bat` 在 Windows 侧直接启动，确保真正 32 位进程。

### Q: MethodHandle.Value 和 GetFunctionPointer 有什么区别？

```
MethodHandle.Value         = MethodDesc 指针（CLR 内部方法描述符）
GetFunctionPointer()       = entry 地址（可能是 precode stub 或真实代码）
```

两者是**不同的地址**，语义完全不同。`Value` 是方法元数据指针，`GetFunctionPointer` 是可调用入口。
